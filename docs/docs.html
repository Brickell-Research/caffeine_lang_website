Documentation

There exist three levels of configurations, each distinct and isolated, referenced by lower levels via unique naming scheme and typically owned by different roles within an organization:

(1) Artifacts: defined by standard library or plugin developers per distinct reliability artifact.

(2) Blueprints: defined by observability experts per artifact abstraction referencing artifacts.

(3) Expectations: defined by the operating team per service referencing blueprints.

Service Expectation Explained

Definition: a service expectation is single blueprint invocation for a single service within the domain of an owning team.

The organization name, team name, and service name are baked in to the filepath path:

ORGANIZATION_NAME/TEAM_NAME/SERIVE_NAME.yaml

As all other configurations, an expectation is a .yaml file with the following required fields.

Attribute Expected Type Description
name String Unique within a single artifacts.yaml file.
blueprint String An identifier referencing a blueprint.
inputs Dict(String, Any) Collection of input names mapped to input values.

So, an example would look like:

expectations:
  - name: "Admin Portal Home Page LCP Latency"
    blueprint: LCP_Latency
    inputs:
      - view: /admin/home
        p95_latency_in_seconds: 5
        threshold: 99.5%
