The Tailless Deno

2026-03-05 · by Rob Durst

I'm building Caffeine, a compiler written in Gleam that compiles service expectations to reliability artifacts. This post documents our migration from Deno to Bun and the tail call optimization rabbit hole that led us there.

We Build with Deno

In my talk at Gleam Gathering, I have a slide where I discuss how we packaged up Caffeine:

Slide 26 from my Gleam Gathering talk, "Packaging Caffeine"

Most of the details can be found in this blog post if you're curious. TLDR is I couldn't quite get the nix setup to work so I ended up compiling to Javascript and then leveraging Deno to package it with a JS runtime. Some more details on this from their website.

Does It Actually Matter?

Well, for what it's worth this is a developer tool which will likely be limited to running on developer laptops (which are typically fairly beefy) or within CICD pipelines. So the 121mb isn't a barrier to entry per se.

The more interesting question is speed and scale: within typical use cases, how fast will Caffeine compile and at what point does compilation become a noticeable bottleneck?

Setting Up Benchmarks

To begin answering these questions, we set up perf: various benchmarks and corpuses and such for caffeine.

The basic idea:

1. Generate a bunch of corpuses of Caffeine blueprints and expectations of varying sizes

2. Script the benchmarking of these corpuses using hyperfine

3. Setup CICD such that we continuously run these benchmarks in a controlled fashion

Ideally this process would be fairly deterministic. We want to control: (a) hardware (running within Github Actions), (b) corpus (consistent between runs), (c) warm-up (need to understand the JS runtime), and (d) build (should use actual Caffeine releases).

However, before going down the determinism rabbit hole (been down there before, in 2019 I did an internship with the Stellar Development Foundation where I spent a bunch of time improving the determinism score in attempt to do some fuzz testing with AFL), let's just get this all setup first.

To bootstrap, I heavily leaned on Claude. I had it put together a corpus generator, wire up hyperfine, and build a script to compare against a baseline. For starters, I decided on the following corpus sizes:

Tail Call Optimization

Ok, so what's actually going on here?

The Short Version

Within the functional programming paradigm, it's quite common for functions to call themselves recursively as the last step if some earlier base case isn't met. When a recursive call is the very last thing a function does (the "tail position"), a smart runtime can avoid pushing a new stack frame entirely, it just jumps back to the top of the function. This is called tail call optimization (TCO).

Consider a tail-recursive loop in Gleam:

fn sum_loop(list: List(Int), acc: Int) -> Int {
  case list {
    [] -> acc
    [first, ..rest] -> sum_loop(rest, acc + first)
  }
}

The recursive call to sum_loop is the very last thing that happens. There's no work left after it returns. That's what makes it a tail call. Gleam compiles to both Erlang and Javascript. On Erlang's BEAM VM, tail calls are optimized natively as the BEAM was designed for this. But on Javascript, it depends on the engine.

V8 doesn't implement tail call optimization. And there's no indication it ever will.

V8 had it behind the --harmony-tailcalls flag around 2016, then removed it. The team cited debugging concerns (tail-called frames disappear from stack traces) and chose developer experience over spec compliance. SpiderMonkey (Firefox) never implemented it either. Thus, even though the ES6 spec mandates proper tail calls, but V8 and SpiderMonkey simply ignore that part of the spec.

Deno uses V8 and so Deno doesn't have TCO.

What Gleam Does About It

The smart folks on the Gleam core team have partially solved this with a loop transformation. When the Gleam JS backend detects a function that calls itself in the tail position, it compiles it to a while(true) loop instead of actual recursion, reassigning the arguments rather than making a new call. With this we get constant stack space. Problem solved!

Except not always...

How result.try Breaks It

Gleam's use syntax is sugar for passing a callback. This:

use #(item, state) <- result.try(parse_something(state))
parse_items_loop(state, [item, ..acc])

Desugars to:

result.try(parse_something(state), fn(tuple) {
  let #(item, state) = tuple
  parse_items_loop(state, [item, ..acc])
})

Which compiles to roughly this JS:

function parse_items_loop(state, acc) {
  return result_try(
    parse_something(state),
    (tuple) => {
      let [item, state2] = tuple;
      return parse_items_loop(state2, [item, ...acc]);
    }
  );
}

function result_try(result, callback) {
  if (result.isOk()) {
    return callback(result.value);
  }
  return result;
}

The recursive parse_items_loop call is in tail position of the closure, but not of parse_items_loop itself. From parse_items_loop's perspective, the last thing it does is call result_try(...). And from result_try's perspective, the last thing it does is call callback(...). Neither of those is a self-call, so neither gets optimized into a loop.

Every iteration adds two stack frames: one for parse_items_loop and one for result_try. With 5,000 expectations, that's 10,000+ frames. V8's stack holds roughly 10,000-15,000 frames.

Same Story for bool.guard

Same pattern, different function. use <- bool.guard(when: condition, return: Error(...)) wraps the recursive call in a thunk passed to bool_guard. The indirection hides the tail call from the compiler, an identical problem to result.try.

And Mutual Recursion

This one is different. Our tokenizer had a chain across three separate functions:

tokenize_loop → emit_token → emit_token_n → tokenize_loop

tokenize_loop matches a character, calls emit_token to record it, which calls emit_token_n to advance the position, which calls back to tokenize_loop to process the next character. The final call is in tail position of emit_token_n, and emit_token_n is in tail position of emit_token, and so on up the chain. But Gleam's JS backend only optimizes self-tail-calls: function A calling function A. It can't see that this chain of three functions is effectively a loop. This is a known open issue.

The Unwrapping

So we unwrapped everything. We replaced higher-order functions with direct case expressions so the recursive call lands in tail position of the function itself.

For result.try:

// Before: closure hides the tail call
use #(item, state) <- result.try(parse_something(state))
parse_items_loop(state, [item, ..acc])

// After: direct case, recursive call in tail position
case parse_something(state) {
  Ok(#(item, state)) -> parse_items_loop(state, [item, ..acc])
  Error(e) -> Error(e)
}

The compiled JS goes from nested closures to:

function parse_items_loop(state, acc) {
  while (true) {
    const result = parse_something(state);
    if (result.isOk()) {
      let [item, state2] = result.value;
      acc = [item, ...acc];
      state = state2;
      // falls through to next iteration — no stack growth
    }
    return new Error(result.error);
  }
}

For bool.guard, same idea: replace the thunk with a plain case so the recursive call is direct.

For the mutual recursion in the tokenizer, we inlined emit_token and emit_token_n directly into tokenize_loop, collapsing the three-function chain into a single self-recursive function. One function calling itself. Optimizable.

All three cases are the same fundamental issue: an intermediary sits between the recursive call and the function that needs to loop. Unwrapping removes the intermediary so the recursive call is a direct self-tail-call.

This worked! The compiler stopped crashing. But we were fighting the engine and more importantly, fighting the language.

Enter the Fine Folks Working on Safari

JavaScriptCore, the engine behind Safari and Bun, is the only major JS engine that implements proper tail calls per the ES6 spec, and has since 2016. They solved the debugging problem with ShadowChicken, a shadow stack that reconstructs eliminated frames in the inspector.

The key difference: V8 doesn't optimize any tail-position calls. JavaScriptCore optimizes all of them, not just self-calls but any call in tail position of any function. So that result_try → callback → parse_items_loop chain... every call in that chain is in tail position of its caller. JavaScriptCore sees that and eliminates the frames. V8 just stacks them up until it overflows.

ASIDE: we're not anti-Deno! It's a great runtime with a strong security model and excellent tooling. But for our specific case (a deeply recursive compiler written in a functional language), V8's lack of TCO was a fundamental constraint. So we switched to Bun.

Bun Migration

The migration was small:

1. Remove npm: import prefixes from a handful of TypeScript files

2. Swap Deno.args for process.argv.slice(2)

3. Change the build command

The compiled Gleam output is pure ESM that runs on any runtime without changes. We then undid all the manual unwrapping, restored result.try, bool.guard, and the natural mutual recursion in the tokenizer. The code is cleaner. It is idiomatic Gleam again. And it's faster!

ASIDE: a caveat this isn't a pure apples-to-apples runtime comparison. v4.5.1 had the manual TCO workarounds in the code while v4.6.0 restored natural recursive style. The speedup reflects the combined effect of switching runtimes and writing cleaner code. We haven't isolated how much comes from JavaScriptCore's raw speed vs. native TCO vs. the code changes themselves.

Conclusion

While we came to define a benchmark, we immediately hit a stack overflow, and following the TCO rabbit hole ended up switching runtimes. What a ride!

Now with the benchmarking pipeline in place, we're set up to track performance as Caffeine evolves. Next up is getting these benchmarks running deterministically in GitHub Actions so we can catch regressions before they ship!
